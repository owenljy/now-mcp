# 2.1.2 transport and discovery validation

This patch addresses the second review of 2.1.1 (`200141e`). No new MCP tool names
are introduced. Existing mailbox envelopes remain supported; new writers use a
versioned length/checksum contract.

Final checks: 603/603 tests passed (including TypeScript compilation), Biome
passed on 98 source files, and `git diff --check` was clean. All five package/plugin
version declarations are 2.1.2. A real stdio MCP client initialized the built
server and listed its 23 tools in 188 ms; the server advertised version 2.1.2.

## Live verification

The existing Desktop YAML was used without editing credentials, changing the
active SDK profile, or altering business records. Background scripts emitted
synthetic output only; their temporary parent/chunks/triggers were checked after
execution. Explicit SDK binding for the verification was in memory only.

- Cross-chunk emoji: 3,504 characters returned exactly, checksum validated,
  `outputStatus:complete`, `cleanupStatus:complete`; 8.185 seconds total.
- 60,000-character output: correctly capped at 56,000, original length retained;
  26.461 seconds total, script 2 ms, persistence 11.286 seconds, cleanup 9.502 seconds.
- The corresponding 2.1.1 unmodified large-output test timed out and took
  199.272 seconds including cleanup. A prior isolated `ignore_cache` experiment
  completed in 36.307 seconds with 20.400 seconds of cleanup. These are single
  observations, not controlled throughput or percentile benchmarks.
- A 1-second deadline during mailbox creation returned an uncertain creation
  outcome in 2.692 seconds, reconciled its unique mailbox name, and never
  submitted a trigger. The mailbox was absent in the follow-up check.
- Duplicate matching SDK profiles returned the original 403 plus an ambiguity
  reason. Explicitly binding the profile verified during review produced a
  successful `now-sdk-query` response (zero rows for this fixture).
- Live `escalat` discovery now ranks `task.escalation` first, ahead of the
  interval/history owner tables, with the same 21-candidate complete window.
- All inspected temporary records from these executions were absent afterward.

## Limits

Cleanup is bounded and best effort. A server-side mutation can commit after a
response is lost; name-based reconciliation does not make arbitrary scripts
idempotent. Incomplete cleanup exposes record names for reconciliation rather
than silently claiming success. The checksum detects accidental corruption and
is not a cryptographic authentication mechanism. Schema ranking is complete only
within the declared candidate window. A real Scripted REST companion endpoint
was not installed for this verification; its uncertain-error path is covered by
fault injection.
