# A2A Secondary-Agent Troubleshooting

On-demand reference for `/sn-aia-a2a-setup`. Every entry below was reproduced
and root-caused on a live instance, in the order they tend to appear when you
follow the vendor playbook literally instead of the corrected
[Setup order](../SKILL.md#setup-order). Check the symptom column first — the
client-visible error is almost always generic or misleading; the real cause is
one or two layers deeper and only visible server-side.

---

## Symptom → cause → fix

| # | Symptom (what the user/caller sees) | Real cause | Fix |
|---|---|---|---|
| 1 | Copilot Studio "Connect Agent2Agent": *"We couldn't find an agent card at this URL"* — but `syslog_transaction` shows a clean `200` for that exact request at that exact second | Browser-side CORS block. The connector's UI fetches the Agent Card **from the user's own browser**, cross-origin. The server responded fine; the browser discarded the response before the connector's JS ever saw it. Confirm via the browser console (F12 → Console): `Access to fetch at '...' from origin 'https://...' has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header...` | Add a `sys_cors_rule` scoped to the `AI Agent A2A API` REST API (`/api/sn_aia/a2a`) with `domain` = the exact origin from the console error (e.g. `https://copilotstudio.microsoft.com`), `get`+`post` = true, `access_control_allow_headers` including `Authorization,Content-Type`. See [table-reference.md](table-reference.md#sys_cors_rule). |
| 2 | *"Missing redirect URL in application registration"* on `/oauth_auth.do` | The `oauth_entity.redirect_url` field is empty. The modern "New Inbound Integration Experience" simplified form **does not expose this field at all** for Authorization Code or "multiple" grant types — there's nowhere in that UI to type it in. | Get the exact value the caller expects from its own OAuth setup screen, or — if it already tried and failed — read the `redirect_uri=` query param off the failed `/oauth_auth.do` request (browser address bar, or `syslog_transaction.url`). Write it directly to `oauth_entity.redirect_url` (classic form `oauth_entity.do?sys_id=...` may also expose it, but UI Policy sometimes hides it there too depending on grant type — don't assume the classic form works either, verify). |
| 3 | `syslog` message `Exception on token flow - invalid_scope: The provided OAuth token is not valid: no thrown error`, client sees a generic `access_denied`/`server_error` on the code→token exchange | The requested scope (usually `a2aauthscope`) was picked in the wizard's "Auth scope" dropdown, which writes to the **new** REST-API-Auth-Scope tables (`oauth_entity_auth_scope_mapping` → `sys_auth_scope`) — but the classic `/oauth_token.do` scope-grant check reads the **old**, separate `oauth_entity_scope` table (plain string, not the same table), which the wizard **never populates**. If `oauth_entity.inbound_grant_type = 'multiple'`, there's a *third* required link: `oauth_entity_profile_scope`, tying the scope to each specific `oauth_entity_profile` (one row per grant type). | Create the missing row(s) directly:<br>`oauth_entity_scope`: `{oauth_entity: <app sys_id>, name: 'a2aauthscope', oauth_entity_scope: 'a2aauthscope'}`<br>If `inbound_grant_type = 'multiple'`: also create `oauth_entity_profile` rows per grant type (`grant_type: 'authorization_code'` / `'client_credentials'`), then `oauth_entity_profile_scope` rows linking each profile to the `oauth_entity_scope` row above. If the app is a *single* grant type (not "multiple"), the plain `oauth_entity_scope` row alone is enough — no profile junction needed. |
| 4 | Same `invalid_scope` symptom as #3, persists after fixing #3 on a **freshly created** app | The wizard also silently sets `oauth_entity.default_grant_type = 'password'` (Resource Owner Password Credentials) regardless of which grant type you actually picked in the UI. This is cosmetic in some paths but check it. | `sn_get_choice_list` on `oauth_entity.default_grant_type` for the real values (`client_credentials`, `authorization_code`, etc.) and set it to match the grant type you actually configured. |
| 5 | `disable_client_restriction` on `sys_api_access_scope` won't update — `403 ACL Exception`, and it **still fails even from a background script with `allowMetadataWrites: true`** (silent `update()` → `null`) | This field is intentionally hard-locked (no admin override). It was a plausible-looking lever during debugging but turned out to be a dead end for this failure chain — don't spend time trying to force it. | Don't touch it. If you're tempted to try this field, you've likely misdiagnosed the failure — go back to #3/#4/#7 first. |
| 6 | End-to-end OAuth works via a manual test client (Bruno/Postman) with the exact same client_id/secret/scope, but the real caller (Copilot Studio) still fails identically | Not a ServiceNow config problem — something client-side: a redirect loop (#8), a stale cached failed-connection state on the caller's side, or the caller hasn't completed its own per-user consent step yet (#9). | Isolate with Bruno first (see [bruno-isolation-test.md](bruno-isolation-test.md)) *before* changing any more ServiceNow config once end-to-end already works there — the fix has moved to the other side. |
| 7 | `400`, `connectorRequestFailure`, or JSON-RPC `-32602 Invalid method parameters: Push Notification URL is required for asynchronous requests` on the **execute** call, after auth already succeeded | `sys_cs_channel` "AI Agent A2A Channel" has `synchronous = false` (the default), and the caller has no push-notification callback registered (`sn_aia_external_agent_callback_registry`) to receive an async response. | Set `sys_cs_channel` "AI Agent A2A Channel" → `synchronous = true`, unless you're deliberately building the async callback path for production. |
| 8 | Browser popup opens `{instance}/oauth_auth.do`, spins on "Signing in…" forever, page content stays blank white. Server logs show a **repeating 3-hop redirect loop**: `oauth_auth.do?scope=...` → `oauth_auth.do?oauth_auth_check_action=authorize` → `oauth_auth.do?scope=...&logoutfirst=false` → repeat | Safari's Intelligent Tracking Prevention (ITP) blocks/partitions cookies for a cross-site popup (the caller's origin opening a popup to `*.service-now.com`), so the popup can never resolve a stable login/session state — it just keeps re-checking and bouncing. | Retry in Chrome or Firefox. This is a browser privacy-policy issue, not a ServiceNow or connector bug — don't spend time trying to fix it server-side. |
| 9 | Copilot Studio test chat: *"Let's get you connected first... Open connection manager to verify your credentials"* even though the OAuth app + CORS + auth profile are all correctly configured | Normal behavior for Authorization-Code-based connectors — each **person** testing/using the bot must complete their own interactive consent once, separate from whether the server-side plumbing works. | Click through "Open connection manager" (or "Retry"), complete the browser login/consent, then retry the message. Not a config bug. |
| 10 | `401 Unauthorized`, `{"error":{"message":"User is not authenticated","detail":"Required to provide Auth information"}}` on the execute call | No bearer token was actually attached to the request — usually because the test tool sent the request without first completing the "Get Access Token" step (fetching a token is a distinct action from sending the request in most OAuth-aware clients; it doesn't happen automatically on first Send in every client). | In the client, explicitly run the token-fetch action (e.g. Bruno/Postman "Get New Access Token") before sending the authenticated request, and confirm a bearer token is actually present in the outgoing request's Auth header before treating this as a server-side bug. |

## Ruled-out dead ends (don't re-litigate these)

- **`sys_api_access_scope.disable_client_restriction`** — hard ACL-locked, not the fix for `invalid_scope` (see #5 above).
- **Editing/deleting the OOB `inbound_auth_profile` "OAuth in External AIA for A2A"** — protection-policy-locked (`sys_policy`), fails even from a background script with metadata-write approval, with the explicit message *"The Protection policy field cannot be changed for application Now Assist AI Agents."* Add a second profile alongside it instead (Setup order, step 7).
- **Assuming the Inbound Auth Profile / API Access Policy layer affects OAuth token issuance** — it doesn't. That layer validates bearer tokens on the *execute* call; it has no effect on the `/oauth_auth.do` → `/oauth_token.do` code exchange. If you're chasing `invalid_scope` during token exchange, look at #3/#4, not #7 in the setup order — conflating the two costs a full debugging cycle.
- **`sys_auth_profile_oauth2`** — looked like the natural place to find the OAuth config underneath an `inbound_auth_profile` record (table hierarchy suggested it), but on the instance this was built against, the table was completely empty even for OOB profiles that work correctly in production. Whatever the modern "Create standard http authentication profiles" wizard actually writes to, it isn't reliably this table — don't assume you can hand-verify the profile's internals this way; verify by testing the flow instead.
